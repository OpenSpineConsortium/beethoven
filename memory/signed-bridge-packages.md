greg, 2026-10-04 15:26Z: "if i have to pay 100 bucks to get it working seamlessly on a mac without any terminal usage i will, i want it to be professional"; 15:41Z (card answer): Option B, the signed package with the binary, and Windows code signing through Azure Artifact Signing (Microsoft's new name for Trusted Signing; Basic plan $9.99/month; sign-in with Entra ID, no key file, which keeps [[no-api-key-anywhere]]).

**Why:** a browser never lets an extension install a program, so the floor is one download and one Install click; only Apple's Developer ID ($99/year) and a Microsoft-trusted certificate remove the "unidentified developer" and "Unknown publisher" moments. Until 14.0.0 the bridge was a Perl/PowerShell script host and the Rust edition (helper/src/rust) was maintainers-only.

**How to apply (the 15.0.0 design, built 2026-10-04 in beethoven-extension):** `beethoven-bridge-mac.pkg` (universal Rust binary, Developer ID Application + hardened runtime, Developer ID Installer, notarized and stapled, installs into the user's home only: `enable_currentUserHome`) and `beethoven-bridge-windows.msi` (WiX v5 per-user MSI, exe and MSI signed with signtool /dlib Azure.CodeSigning.Dlib.dll /dmdf metadata.json, timestamp http://timestamp.acs.microsoft.com), built ONLY on greg's machines by `helper/release/mac/build-pkg.sh` and `helper/release/windows/build-msi.ps1`; outputs plus a sidecar JSON land in gitignored `helper/signed/`; `node helper/build.mjs` verifies the sidecar (helper version, sha256, origins, "signed") and adds `kind:"binary"` entries with `allowed_origins` to `extension/public/bridge/manifest.json` (that manifest is not committed on a release). The store item id is baked in (`--store-id`, read in the store dashboard; greg has not given it yet); the picker offers a binary only when its origins name `chrome.runtime.id`, so development builds and Linux keep the script zips. Terms: LICENSE.txt 10 / PRIVACY.md 11 / TERMS_VERSION 10, dated 2026-10-04; the Rust std notice joins THIRD_PARTY_NOTICES. The helper stays 1.0.0, protocol 1. Signing identities never enter the repository or CI. learn.microsoft.com is unreachable from the cloud (proxy 403): the Dlib package name and endpoints are parameters greg checks. Nothing about Gatekeeper, SmartScreen, Installer.app or Chrome starting the binary is measured: "not yet measured" until greg runs it on real machines. greg's hand steps: Apple Developer Program enrolment, two Developer ID certificates, a notarytool keychain profile; an Azure subscription with an Artifact Signing account, identity validation and a certificate profile.

Release on greg's Mac only (his asks 19:26Z and 19:33Z, card "Save on Mac" 19:36Z): one command on the Mac builds and signs both installers (the Windows MSI cross-built: msitools `wixl`, Rust target x86_64-pc-windows-gnu with mingw-w64, jsign 7.5 against Artifact Signing with an `az` access token), zips one package carrying both, and uploads it with `helper/release/publish-store.mjs` (Chrome Web Store API v2 upload/publish/fetchStatus; Private listing with a Google Group of testers needs no Workspace; Google reviews every version). The store's Google sign-in (Desktop OAuth client + refresh token) is saved 0600 in the vendor folder `chrome-web-store/`, never in a repository or CI. No Windows machine needed.
