# Beethoven project instructions (version 11, 2026-10-04)

## 1. What this project is
Beethoven is two systems sharing one university cluster. The launcher (repos OpenSpineConsortium/hpcworker and beethoven-extension) runs a student's own Claude Code as an always-on Slurm job in an Apptainer image, reached through Claude Code Remote Control. The research engine is an autonomous prompt-to-paper pipeline in three repositories under OpenSpineConsortium (greg, 2026-10-04): beethoven-qa (how code is written and proven: pixi, contracts, the CrossHair gate as a command, the repository rules, a Claude Code plugin), beethoven-agents (how agents run on the grid: the image, guard, accounts and hand-off, the Metaflow loop around headless `claude -p`, pacing, registry) and beethoven-research (what is computed and shown sound: REFORMS, CLAIM, calibration, publication, the studies). qa <- agents <- research is the only direction of dependence; a change that needs an upward import is in the wrong repository. Owner: Gregory Schwing (greg), Wayne State grid account go2432. Study repos: Gregory-Schwing-MD-PhD/spinesurg-ct-nnunet and u251-xenograft-rat-RNASeq-study. Plans: /mnt/project-files/plan/ (BUILD_PLAN.md governs); tasks: Linear team Beethoven; every unit of work: /mnt/project-files/ledger/LEDGER.md. The build is itself the subject of a methods paper (BUILD_PLAN.md section 12), so the record of how it was built is a deliverable, not housekeeping. The two repository CLAUDE.md files stay binding; where this page and they disagree, the stricter rule wins and you say so.

## 2. Credentials and billing: entire dependence on the student's own flat-rate sign-in (D1, decided by greg 2026-10-03)
- Everything that calls Claude, interactive or headless, runs on the student's own flat-rate Claude subscription through the sign-in Claude Code holds after `claude auth login` (in the profile's `claude_config_dir`). Since 2026-06-15 `claude -p` and the Agent SDK draw on that plan; console keys cannot reach it.
- Therefore: no Anthropic console API key anywhere, no pooled or lab-held key, no commercial key, no LiteLLM or other gateway, no Bedrock or Vertex, no key rotation, no licence keys. Managed Agents and the raw Messages API need a key, so they are out. Usage credits (paying past the plan's limit) are never used: a hard exclusion of the same rank as every other rule here (greg, 2026-10-04). The engine never turns them on and never asks a student to. Several of greg's own accounts run at once (BUILD_PLAN section 17 and D1d, greg 2026-10-04): each signed in by him into its own directory, one master job per account, one account holding the super-master lease at a time and handing it to the next as its window nears its limit; the run carries over from the engine's saved state, which includes the guide's six-section hand-off file (`state/claude_context.md`, read back through `state/HYDRATE.md`), and the near-limit session itself may continue under the next account from its transcript, by the absolute path Claude Code reported to its own hook, as `--resume <path> --fork-session` with the file bound read-only (BUILD_PLAN 17.2.9, built only after probe M13). The engine holds directory paths and labels only, never looks inside or copies between them, logs every switch, and never uses anyone else's account. No pooled tokens, nothing that evades detection; a spent account hibernates until its reset. A design that needs any excluded thing is wrong; stop and say so.
- Our software never reads, stores, copies, prints, relays or exports a Claude credential: no `setup-token`, no `CLAUDE_CODE_OAUTH_TOKEN`, no `ANTHROPIC_API_KEY`, no reading `.credentials.json` under any config directory. The student signs in on a compute node themselves. We only start Claude Code where its sign-in already is (`CLAUDE_CONFIG_DIR` set to that directory, bound read-write for Claude Code's own writes and protected by policy, never by a mount flag) and read `claude auth status`. Every credential variable is removed from a job's environment. `claude auth logout` is never run, and the guard refuses `claude auth login` and `claude project purge`. An account counts as signed in only when `claude auth status` says `authMethod: "claude.ai"` for that directory.
- Tokens and secrets never appear on command lines, in argv, in logs, in job files, in `sbatch --export`, in the ledger or in Linear. The per-job token of the launcher is a mode-0600 file. Never echo one.
- All automated runs share the student's rolling 5-hour usage window with their manual sessions. Rate limits are met by pacing inside that window (section 5), never by routing, extra keys or evading detection; the only account change is the super-master hand-off.
- Where the extension is concerned: no code on claude.ai, no content script, host permission or fetch patch there; never the permissions the CLAUDE.md forbids; never a claude.ai, anthropic.com or claude.com origin; no remote code. The consent signal is Claude Code's own (`remoteDialogSeen`, `hasTrustDialogAccepted`); read those two keys only and never rewrite that file beyond the three seeded keys.

## 3. Never destroy, never exceed scope
- Nothing is deleted outside the framework's own run directories and node-local temp: never the Claude login directory, the workspace, another run, or anything else under `$HOME`. A destructive subcommand refuses when `CLAUDECODE`, `BEETHOVEN_REQUEST_ID` or `ASHLEY_REQUEST_ID` is set or stdin is not a terminal.
- Engine state goes to Postgres or node-local SQLite, never into the student's Claude configuration.
- Goal 4 security work on the grid is governance only: the PreToolUse guard hook, managed-settings deny rules, authorized-target lists, the air-gap boundary. Exploit or proof-of-concept generation is off-grid, private and out of scope here.

## 4. Definition of done for every module (the bug-proof checklist, Goal 1)
No code, hand-written or generated by the engine, may enter a research run until all seven hold:
1. Deterministic environment: a Pixi lockfile (exact versions, build strings, hashes) and a hashed Apptainer image built `--fakeroot` and run `--containall --cleanenv --no-home`.
2. Design by contract: icontract `@require`, `@ensure` and invariants on every public function; subclasses only weaken preconditions and strengthen postconditions.
3. Layered runtime types: pydantic at external boundaries, beartype on internal hot paths, typeguard in tests.
4. Symbolic proof: CrossHair with Z3 finds no input that satisfies the preconditions and violates the postconditions within a declared bound (concrete loop bounds, I/O stubbed at the edges).
5. Schema-aligned parsing for every LLM output: BAML/SAP with coercive repair and validation feedback, never raw JSON mode and never a hard crash.
6. The self-healing loop: generate code and contracts, compile, run CrossHair, feed counterexamples back, iterate until proven. Humans review contracts, not lines.
7. The gate runs before every push and no human gates a merge (greg, 2026-10-04): all of the above runs, as beethoven-qa's gate from each repository's pinned copy, as a pre-push hook and as the required CI check; pull requests open ready for review with auto-merge enabled, and the required checks alone decide the merge; a failing module reaches neither a run nor `main`.
Also: every long-running step declares how it can tell it is making progress (an objective, a reference or a test suite) and commits after each unit of work; a step that declares none is not scheduled (BEE-178). Reproduce a bug before fixing it; a test is never skipped, disabled or quarantined to get green.

## 5. Token economics (always on, every engine run, Goal 3)
1. Lazy tool loading (`ENABLE_TOOL_SEARCH`, mcp-cli): MCP schemas fetched on demand, never injected up front.
2. Prompt-cache TTLs in managed settings: `promptCacheTtl` 1h for the lead agent, `subagentPromptCacheTtl` 5m for subagents.
3. Preemptive compaction in grid jobs: `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=65` together with `CLAUDE_CODE_AUTO_COMPACT_WINDOW=1000000` (the override alone is unreliable headless); a launch uses `--autocompact <size>`; never type `/autocompact`, which writes into the sign-in directory.
4. State across compaction: a PreCompact hook writes decisions and paths to node-local `scratchpad.json`; a SessionStart hook (compact matcher) re-injects them.
5. Concurrency is bounded by each account's window and the node's cores, not by a count of nodes (greg: compute is not the scarce thing): `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` and teammates per master at most the allocated cores, spawn depth 1, at most 50 subagents per session.
6. Quota-window pacing instead of a gateway: the orchestrator records each step's tokens, holds the next step or branch when the window is nearly spent, and hands the super-master lease to the next account or hibernates the job until the window rolls, never retrying. An interactive session's status line receives `rate_limits` (5-hour and 7-day `used_percentage`, `resets_at`); whether they arrive on the grid, and how a `-p` step learns its window, are not yet measured (BEE-121).
7. Nested loops: the outer Metaflow loop owns state, requeue and routing; the inner `claude -p` owns code; intermediate state lives in variables and the database, not the context window. Agent teams are in (greg 2026-10-04; BUILD_PLAN section 17): masters are interactive leads under a pseudo-terminal, teammates in-process, never tmux; a master runs unattended, so teammates never prompt (probe M12) and the PreToolUse guard stays in force; sessions beyond the node are new Slurm jobs registered with their parent first; cross-account messages go over the engine's bus only; nothing is ever orphaned: registry, heartbeats, a reaper cancelling only our own registered jobs.
8. Measure every run: tokens in and out, cache hit rate, compaction events, subagent count, wall clock and energy, into the ledger and W&B.

## 6. REFORMS compliance (Goal 2)
Every study the engine runs clears the 32 REFORMS items: 20 checked by code gates, 12 declared in the study's `study.yaml`. The gates: a Run ID hashed from the lockfile, image, code tree and inputs (volatile Slurm variables excluded); a clean-tree gate (no uncommitted changes); a run manifest and compute record (`reforms.json`); patient-level data splits with no patient on both sides; bootstrapped confidence intervals on every reported metric; CodeCarbon energy per run. Figures and tables are regenerated from code, and a `make`-style check exits non-zero when a reported number has moved.

## 7. CLAIM compliance (medical imaging studies)
Any imaging study reports against all 42 items of CLAIM (the checklist in spinesurg-ct-nnunet). A manuscript draft carries a filled CLAIM table; a missing item is named, never papered over. Medical calibration (Goal 6): Hounsfield-unit calibration is checked on every CT corpus and MONAI MetaTensor metadata (spacing, orientation, affine) is asserted intact through every transform.

## 8. Grid etiquette (and who said what)
- On the login node (`warrior`) nothing of ours runs beyond `bash` and one `sbatch`, `squeue` or `scancel` per action. Its banner bans `python3`, `node`, `rsync` and `md5sum`, so Metaflow runs in a compute-node orchestrator job (chained with `afterany`) or on the student's machine. Nothing container-related there and nothing of ours under its `/tmp` (C&IT's instruction, 2026-09-28).
- Container temp and cache on the compute node's local disk, `/tmp/$USER/hpcworker_$SLURM_JOB_ID`, with a cleanup trap; `$TMPDIR` on Wayne State points at CephFS and is never trusted. IPC under `/dev/shm`.
- Clients poll the scheduler no faster than every 60 s; the job writes `status.json` and clients read the file. Every job has a wall time. These two are the product's own etiquette, not C&IT's. The 20-process login-node cap is Wayne State's published policy.
- Chain with `afterany`, never `afterok`; `#SBATCH --output` resolves against the submit directory (use `-D`); `/tmp` is swept while jobs run.
- Anything that runs a container, a scheduler call or Claude Code runs on the grid inside a Slurm job, never on the login node, never on a laptop and never from a cloud session.

## 9. Data and PHI
- Patient data never leaves the grid. DICOM headers carry names and dates; catalogs hold metadata only; whether identifying columns may exist follows from greg's PHI statement (BEE-165). Splits are patient-level.
- The imaging migration to CephFS (BEE-165) is copy, verify by hash manifest, lock read-only, never delete; greg decides deletions by hand; nothing runs against the grid until he names sources, destination and PHI statement and the inventory job has measured.
- Home secrets (`.hf_org_token`, `.hf_osc_token`, `.kaggle`, `.wandb`) are never read or copied; branch `L6_Class` of spinesurg-ct-nnunet stays private, never pushed to a public repository.
- Publication (Goal 7: Zenodo DOIs, Hugging Face model cards, OpenLineage and RO-Crate records) happens only behind a human Publish click.

## 10. Measurement: the ledger
The whole build is itself a study. Every thread appends one row per unit of work to /mnt/project-files/ledger/LEDGER.md: `date_utc | thread | actor | activity | wall_min | bugs_fixed | inputs | outputs | verified` (`verified` is `independent` only when another route confirmed it). Append-only, UTC, nothing secret in it. Every human intervention, answer, failure, dead end and withdrawn claim goes into ledger/INTERVENTIONS.md the moment it happens, with why (knowledge, permission, error, requirement or decision), never reconstructed later. ledger/BOUNDARY.md records what each agent could and could not touch, per phase. Engine runs add Slurm job ids, partition and QoS, wall time, queue wait, GPU-hours, preemptions, window spend (tokens, cache hits, compactions, subagents, account) and energy, linked from the row. Prompts, instruction files, agent logs, job scripts and git history are kept whole. The thread doing the work updates its Linear issue.

## 12. How to work here
- Check every number and state against something outside the computation (a log line, the portal's response, a file) before repeating it. Say plainly what is not known; "not yet measured" is the preferred form.
- Open decisions belong to greg and are logged (BUILD_PLAN.md section 7, Linear label `decision`): pick the reasonable default for anything smaller, say which, and keep going. Never ask greg for a credential or to paste one anywhere.
- Build order (BUILD_PLAN section 5): the substrate with the verification gate first, then verification, orchestration and quota pacing, REFORMS and medical calibration, guard hooks from the first real run, publication behind the human gate, the clients.
- Parallel work runs in git worktrees (`--worktree`; subagents with `isolation: worktree`); repeatable fan-outs are workflow scripts saved in `.claude/workflows/`, concurrency at most the allocation's cores; a step removes its own worktrees when it ends, never the retention sweep; a headless workflow run that hits the limit is resumed by the same account after its reset, never moved to another (BUILD_PLAN 17.6).
- Read-only neighbours: Beethoven for VS Code and the study repositories are never edited from here.
